## 遇到的问题和解决

1. 问题：文档示例使用 `coverage run -m pytest` 再执行 `coverage report`，与仓库已启用 **pytest-cov** 冲突，易出现「No data to report」。  
   **解决**：以 **`pytest`** 为准（与 CI 一致），由 `pytest.ini` 统一生成 `coverage.xml` 与 `htmlcov/`。

2. 问题：CI 无本地 MySQL，需保证测试在默认配置下可运行。  
   **解决**：测试侧沿用内存库 / 测试配置（见 `tests`、`conftest`），保证 **Pytest with coverage** job 稳定通过。

## 心得体会

通过本次 CI/CD 配置，我体会到「本地能跑」只是第一步，**与远程 Ubuntu、固定 Python 版本和默认工作目录对齐**后，才算真正可靠。把 **Ruff** 纳入流水线后，风格问题会在合并前暴露，比事后人工审查更省时。覆盖率方面，最初照搬教程里的 `coverage run` 与项目里的 **pytest-cov** 叠用反而出错，说明**一定要读清本仓库的 `pytest.ini` 和 CI 脚本**，不能盲抄模板。

Codecov 与 README 徽章让我们能直观看到后端测试覆盖是否在回落，有利于长期坚持补测试。整体上，CI 不是写完就结束的文档，而是需要随着依赖和测试策略一起维护的工程习惯。
